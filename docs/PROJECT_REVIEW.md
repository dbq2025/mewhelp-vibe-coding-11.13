# 项目复盘：把「电商智能客服」当成一次 AI 工程训练

> 面向学习者的总结。不是功能说明书（那是 README），也不是接口文档（那是 api.md），
> 而是回答一个问题：**这套东西为什么这么长，每一步的判断依据是什么，哪些能力可以搬到下一个项目。**

---

## 0. 先看结论：六句话

1. 这个项目的核心不是"接了个大模型"，而是**把不确定的模型输出关进确定的工程结构里**。
2. 分层的目的不是好看，而是**每一层都能被单独验证**：SQL 能测、纯函数能测、节点能用假模型测、契约能用 httpx 测。
3. Agent 的部分刻意做小：**7 类意图、8 个节点、4 步工具预算**，剩下的全交给确定性代码。
4. 真正的难点在写操作：**二次确认、幂等、越权、中断落库**，漏任何一件都是线上事故。
5. AI 写了约 90% 的代码，但**四个判断始终在人手里**：边界、契约、验收口径、偏差是否可接受。
6. 最可复用的不是 prompt 技巧，而是 **agent.md + 契约文档 + 评测集 + 假件替换 + 证据驱动** 这套"给 AI 装护栏"的流程。

**学习提示**：如果你只记一件事，记第 6 条。模型会换、框架会换，这套流程不会。

---

## 1. 项目全貌

### 1.1 它做什么，不做什么

**能做**：商品检索 / 详情 / 对比、订单与物流查询、售后政策问答、售后受理（退货 / 换货 / 退款）、转人工。

**不做**（边界和功能同样重要）：

- 不下单、不支付、不改地址 —— 涉及资金与外设系统，超出可信边界
- 不承诺赔付、不判断"谁的责任" —— 这类结论必须由人给出
- 不查他人订单 —— 越权与"查不到"返回同一个码
- 没有客服工作台 —— 转人工只落工单，不做坐席端

**点评**：一个能演示的项目和一个能交付的项目，差别就在"不做什么"这一节。
AI 天生倾向于把功能铺满，**主动砍边界是人必须做的动作**。

### 1.2 一次请求穿过哪些层

```
浏览器  Vue 3 + Pinia
   │  HTTP（JSON envelope）/ SSE（8 类事件）
   ▼
API 层   api/routers
   │  契约校验 · 鉴权 · 幂等重放 · 错误码映射
   ▼
Agent 层 agent/graph.py
   │  guard → understand → 路由 → 节点 → compose
   │  旁路：RunContext（DB 会话 / 用户 / trace / 工具预算 / 计量）
   ▼
Domain 层 domain/policies + domain/services
   │  纯业务规则：可受理判定、鉴权、状态机、聚合
   ▼
Infra 层 infra/db
   │  SQLAlchemy 2 async + asyncpg
   ▼
PostgreSQL 16 + pgvector
```

横向切面 `core/`（配置、错误、日志、trace、安全、限流）被所有层依赖，
但**不允许反向依赖业务** —— 这条铁律保证 `core` 可以被复制到下一个项目。

**点评**：判断分层是否真的成立，有个简单测试：
**把 Agent 层整个删掉，API + Domain + Infra 还能不能跑？**
本项目能——`/products`、`/orders`、`/after-sales` 都不经过图。
做不到这一点的"分层"，通常只是把代码分文件夹放。

### 1.3 目录即架构

- `api/routers/` — 只做三件事：收参、调 service、包 envelope。不写业务判断
- `api/schemas/` — Pydantic v2 契约，请求与响应各一套，**不直接暴露 ORM 模型**
- `agent/` — 图、节点、工具、槽位、prompt、运行上下文、LLM 客户端
- `domain/services/` — 可被 HTTP 与 Agent 同时调用的业务函数（售后、订单、账号、会话、指标）
- `domain/policies/` — 鉴权这类"横穿多个 service 的规则"
- `infra/db/models/` — 按领域拆文件（user / catalog / order / chat / kb / ops）
- `rag/` — 分块、分词、向量化、检索，与 Agent 解耦
- `scripts/` — seed、灌库、评测、演示排练，**也是"可执行的验收"**
- `tests/` — 按 `unit / api / graph` 三层组织，对应三种验证手段

**点评**：`scripts/` 被当成一等公民而不是临时工具，是这个项目能持续验收的关键。
`eval.py` 和 `demo_check.py` 让"跑一遍看看"变成了可重复、有输出的动作。

### 1.4 规模（用来判断复杂度是否失控）

- 后端源码 **7111** 行，测试 **2113** 行，脚本 **1818** 行；前端 **2222** 行
- **15** 张表、2 个迁移、约 20 个端点、6 个工具、8 个 SSE 事件
- 后端 **151** 个测试、前端 **13** 个测试

**学习要点**：测试与源码的比例约 1:3.4。这个比例不是标准，但它说明一件事——
**AI 写得越快，"验证的密度"越要跟上**，否则你只是把 debug 从写代码阶段推迟到演示阶段。

## 2. 模块拆解

每个模块按同一结构讲：**职责 → 实现思路 → 关键逻辑 → 取舍 → 点评与学习要点**。
建议按顺序读，因为后面的模块依赖前面的契约。

### 2.1 契约层：先写文档，再写代码

**职责**：定义"前端能依赖什么"，把变化挡在 API 边界之外。

**实现思路**：

- 统一响应 envelope：`{"code": 0, "message": "ok", "data": {...}}`，错误也走同一形状
- 错误码分段：`2xxx` 参数/鉴权、`4xxx` 业务状态、`5xxx` 系统
- 分页用 **cursor** 而不是 offset：`(price, id)` 二元组编码
- 契约文档（`docs/api.md`）先于实现写，实现完回填版本号

**关键逻辑**：

```python
# 越权与"不存在"返回同一个码：不给扫描器确认订单是否存在
raise NotAllowedError()   # code=2003 → HTTP 403/404 同码
```

```python
# cursor 分页：排序键重复时用 id 兜底，否则会漏数据
WHERE (price, id) > (:last_price, :last_id) ORDER BY price, id LIMIT :n
```

**取舍**：offset 分页实现更简单，但翻页时会因新数据插入而重复/漏项；
本项目商品列表价格有大量并列（不同 SKU 同价），**必须用复合游标**。
代价是前端不能"跳到第 5 页"。

**点评**：契约层最容易被 AI 做坏的地方是"顺手多加个字段"。
一旦前端开始依赖 `data.items[0].extra`，这个字段就删不掉了。
本项目的做法是：**任何一个新字段，先问它属于哪个既有结构，能不能不加。**

**学习要点**：

1. envelope 和错误码要在写第一个接口前定死，改一次全链路都要改
2. "不存在"与"无权限"合并同码，是安全设计不是偷懒
3. 分页键必须唯一且稳定，**排序字段重复时一定要带 id**

### 2.2 数据层：15 张表怎么长出来的

**职责**：让每一条业务事实都有唯一归属，且约束写在数据库里。

**实现思路**：按"谁产生、谁读取"分五组：

- 身份：`users`
- 商品：`categories` → `products`
- 交易：`orders` → `order_items`、`shipments`、`after_sales`
- 对话：`sessions` → `messages`、`session_states`、`handoff_tickets`
- 知识：`kb_docs` → `kb_chunks`（`vector(1024)` + HNSW）
- 运维：`llm_usage`、`audit_events`

**关键逻辑**：

```python
# 约束下沉到 DB：应用层判断会被并发绕过
UniqueConstraint("order_no", "type", name="uq_after_sales_order_type")
# 部分唯一索引：已取消的单不占用唯一性
Index("uq_after_sales_active", "order_no", "type",
      unique=True, postgresql_where=text("status <> 'cancelled'"))
```

**取舍**：`session_states` 单独一张表（而不是塞进 `sessions.metadata` JSONB）。
理由是槽位会被**并发写**，独立行可以用 `UPDATE ... WHERE version = ?` 做乐观锁；
代价是多一次 JOIN。

**点评**：本项目最值钱的一条数据经验是 **"给已有数据的表加 NOT NULL 列"**：

```text
直接 ALTER TABLE ADD COLUMN ... NOT NULL   → 失败（存量行没有值）
正确姿势：加可空 → UPDATE 回填 → 改非空（三步，同一迁移内完成）
```

这是 AI 很容易写错、而且**在空库上测试完全发现不了**的坑。
它说明一件事：**迁移必须在"有数据"的库上验证**，而不是在 CI 的空库上。

**学习要点**：

1. 唯一性、外键、非空，能在 DB 表达的不要只写在 Python 里
2. 幂等靠"唯一索引 + 捕获冲突"，不靠"先查再插"（后者有竞态）
3. 迁移要可 downgrade，且要在有存量数据的库上跑过一遍

### 2.3 检索层：分块、向量、混合排序

**职责**：把 25 篇政策文档变成"能回答问题的最小片段"。

**实现思路**（四步，每步都能单独评）：

1. **分块**：按二级标题切，块前拼标题前缀（`《运费规则》> 退货运费`），让孤立片段自带上下文
2. **向量**：`bge-m3` 1024 维，HNSW + `vector_cosine_ops`
3. **关键词**：中文没有空格，`jieba` 装不上（构建期要批量删临时文件，被安全策略拦），改为**自研字符 bigram** + `tsvector`
4. **融合**：RRF（Reciprocal Rank Fusion），k=60，标题命中额外加权

**关键逻辑**：

```python
# RRF 只看排名，不看分数：向量距离"越小越好"、ts_rank"越大越好"，量纲不可比
score += 1.0 / (k + rank)          # 向量路
score += 1.0 / (k + rank)          # 关键词路
score += title_match_ratio / (k+1) # 标题命中，轻加权
```

**取舍与诚实结论**：

- 不用 `jieba`：装不上是事实，自研 bigram 效果够用且零依赖
- 混合检索在本语料上 **hit@3 没有提升**（纯向量已 10/10 饱和）。仍然保留，因为
  **关键词路是向量服务的降级路径**——embedding 接口挂掉时还能检索
- 这条写进了 `docs/eval.md`，没有粉饰成"混合检索提升 X%"

**点评**：这是全项目最值得学的一段"工程诚实"。
指标饱和时，继续吹混合检索是自欺；但直接删掉关键词路又是把可用性赌在第三方 API 上。
**正确做法是保留但重新定义它的价值：不是提效果，是提供降级。**

**学习要点**：

1. 分块要带标题前缀，否则"48 小时"这种片段脱离语境就无法判断适用范围
2. 融合排序优先用 RRF，不要一上来调权重——**量纲问题比权重问题更常见**
3. 指标没提升要如实写，同时说清楚"那它为什么还在"

### 2.4 Agent 图：把模型关进流程图

**职责**：决定"这一轮怎么走"，不负责"记住上一轮"。

**实现思路**：

```text
START → guard ─┬─ blocked ────────────────────────→ static → END
               └─ continue → understand ─┬─ clarify → clarify → static
                                         ├─ handoff → handoff → static
                                         ├─ after_sales → after_sales → static
                                         ├─ sales_agent ─┐
                                         ├─ order_flow ──┼→ compose → END
                                         ├─ retrieve ────┤
                                         └─ chitchat ────┘
```

- **7 类意图**只在 `state.py` 的 `Intent` 枚举里定义一次，prompt / 路由 / 评测集共用
- **8 个节点**，每个节点只返回自己负责的字段（`GraphState` 全字段可选）
- **不引入 checkpointer**：每轮由 runner 从 `session_states.slots` + 近 12 条消息重建

**关键逻辑**：

```python
# 意图收敛：模型给出没见过的标签时走兜底，绝不让它 500
def parse_intent(raw: object) -> Intent:
    for intent in Intent:
        if str(raw).strip().lower() == intent.value:
            return intent
    return INTENT_FALLBACK      # chitchat
```

```python
# 低置信但用户已经给了订单号 → 不再反问
if intent in ORDER_INTENTS and order_no_in_text:
    route = Route.ORDER
elif confidence < 0.60:
    route = Route.CLARIFY
```

**取舍**：不用 checkpointer 是**主动放弃** LangGraph 的一项能力。
理由是它会和业务 `messages` 表形成双真源——出问题时无法判断以谁为准。
代价是每轮重建状态（约 10ms），收益是"图崩了"和"数据丢了"可以分开排查。

**点评**：这是本项目最重要的架构判断。
很多人用 LangGraph 的第一反应是"上 checkpointer 做记忆"，但**记忆一旦有两份，就一定会不一致**。
判断标准很简单：**这份状态谁是权威？** 如果答案是数据库，那图里就不该存。

**学习要点**：

1. 意图枚举只能有一处定义，否则 prompt 写 8 类、代码处理 6 类，早晚漂移
2. 模型输出的标签必须收敛到枚举，**未知值走兜底而不是抛异常**
3. 低置信不等于必须反问——**已经拿到关键槽位时就该往前走**
4. "不用某个框架能力"也是设计决策，要写进文档并说明代价

### 2.5 写操作闭环：本项目真正的难点

**职责**：让"我要退货"这句话，最终变成一条可追责、不重复、不越权的工单。

**实现思路**（四道闸，缺一不可）：

1. **鉴权**：先查订单归属，失败只记审计、不泄漏存在性
2. **可受理判定**：`check_eligibility` 纯函数（状态 / 时效 / 类型组合），不碰 DB
3. **二次确认**：模型只负责"提议"，是否执行由**规则**判定
4. **幂等**：唯一索引兜底，重复提交返回同一工单号 + `created: false`

**关键逻辑**：

```python
# 确认判定写在规则里，不交给模型措辞
def classify_confirmation(text: str) -> str:
    t = text.strip()
    if len(t) > 8:              # 长句里往往还有新信息，不当作确认
        return "unclear"
    if _DENY.match(t):          # 否定优先："不用了""算了" 先判
        return "deny"
    if t.startswith("不"):      # "不要了" / "不退了"，一律按否定
        return "deny"
    if _CONFIRM.match(t):
        return "confirm"
    return "unclear"
```

```python
# 幂等：先查后插有竞态，靠唯一索引兜底
try:
    session.add(ticket); await session.commit()
except IntegrityError:
    await session.rollback()
    ticket = await get_existing(...)   # 返回已有单，created=False
```

**取舍**：

- **终态文案全模板**，不让模型写"已为您提交成功"。模型可能编造单号或承诺时效
- **待确认动作存 `session_states.pending_action`**，而不是让模型在下一轮"记得"
- 工单号用 PG 序列生成，不用 UUID：可读、可排序、可口头报

**点评**：这一段是全项目"AI 应用"与"AI 玩具"的分水岭。
判断标准只有一句：**这个动作错了，谁承担后果？**
如果答案是"用户/公司"，那这个动作就不能由模型自由决定。

**学习要点**：

1. 写操作必须有"提议 → 确认 → 执行"三段，**中间那段由规则把关**
2. 确认判定要处理：太长（含新信息）、否定词、反问、表情
3. 幂等靠 DB 约束，不靠应用层判重
4. 终态文案模板化，是**降低幻觉面积**最便宜的手段

### 2.6 流式链路：SSE 与前端状态机

**职责**：让用户在 1 秒内看到第一个字，并且界面状态永远和服务器一致。

**实现思路**：

- 服务端：`astream(stream_mode=["custom","values"])`，节点用 `emit()` 推**语义事件**
- **8 类事件**：`meta`（意图/置信）、`slots`（槽位变化）、`tool`（start/end）、
  `action`（卡片）、`delta`（文本增量）、`citation`（引用）、`error`、`done`
- 前端三段分离：`lib/sse.ts` 纯解帧（可单测）→ `useChatStream` 传输 → `stores/chat.ts` 状态机

**关键逻辑**：

```text
服务端不做"前端要什么"，只做"发生了什么"：
  ✗ {"text": "正在查询订单…"}      ← 前端无法区分是提示还是答案
  ✓ {"type":"tool","status":"start","name":"get_order"}
```

```ts
// 前端只认事件，不猜文本
switch (event.type) {
  case 'meta':  /* 记录 intent/confidence */
  case 'delta': /* 追加文本 */
  case 'action':/* 渲染确认卡片 */
  case 'done':  /* 落 status，解除 streaming */
}
```

**取舍**：

- SSE 而非 WebSocket：单向推送够用，且能复用 HTTP 鉴权与中间件
- **输出校验带 hold-back**：`StreamingScrubber` 先扣住 40 字符再吐，
  否则单号被替换时已经流到浏览器了
- 中断用**独立 DB 会话 + `asyncio.shield`** 落 `incomplete`：
  同一会话此时可能已被取消，复用会一起回滚

**点评**：流式最容易被忽略的是"失败路径"。
本项目在 P2 花了大量时间处理：客户端断开、模型超时（已吐出部分内容就不能重试）、
并发同会话、重放幂等。**这些都不在"功能列表"里，但决定项目能不能演示。**

**学习要点**：

1. SSE 事件要表达**语义**，不要表达"该显示什么"
2. 流式场景下"重试"要区分"已吐出"和"未吐出"，前者不能重试
3. 落库用独立会话，否则会和已被取消的请求一起回滚
4. 解帧逻辑与业务逻辑分开，前者才能被单测覆盖

### 2.7 质量与可观测：让"感觉还行"变成数字

**职责**：把"能不能上线"变成可复现的判定。

**实现思路**：

- **评测集**：60 条意图+工具标注、10 条对抗（5 注入 + 5 越权），每条独立会话
- **`scripts/eval.py`**：意图混淆矩阵 / 工具集合精确匹配 / 延迟分位 / 成本 / 对抗结论
- **限流**：滑动窗口中间件（IP 30/min），`429 + 4029 + Retry-After`
- **计量**：LLM 每次调用（含重试失败）记到 `RunContext.llm_calls`，与消息**同事务**落表
- **看板**：`/admin/metrics` 只出聚合值，口令为空则 404

**关键逻辑**：

```text
门槛表（写进计划，不达标改代码不改门槛）
  意图准确率    ≥0.90     实测 0.983
  工具集合匹配  ≥0.85     实测 0.983
  首字 P95      ≤2.5s     实测 2.36s
  单轮 P95      ≤12s      实测 2.80s
  单轮成本      ≤¥0.01    实测 ¥0.00086
  注入拦截      ≥9/10     实测 5/5
  越权泄漏      0         实测 0/5
```

**取舍与诚实记录**：

- 意图唯一判错的是 `i46「支付失败但已扣款」`：标 `policy_faq`，模型给 `after_sales`。
  **保留不删**——它暴露的是真实歧义，删掉等于把指标做漂亮而问题还在
- "事实支撑率"改为机器可判的**锚点覆盖率**（政策看引用、订单看单号、商品看数字），
  另加 8 条人工抽查。锚点 0.786 不进门槛表，因为它只判"有没有可核对信息"，不判对错

**点评**：这一段最值得学的是**"指标不达标怎么办"的决策顺序**：
先确认是不是标注错了 → 再确认是不是实现错了 → 最后才考虑改门槛，
而改门槛需要写进偏差记录并说明理由。

**学习要点**：

1. 评测集要包含"会判错的边界样本"，全对的集通常说明太简单
2. 机器指标要标明它**测的是什么、测不了什么**，否则会被当成万能结论
3. 成本、延迟、错误率要能从同一张表查出来，否则优化没有方向
4. 限流的关闭开关要走配置（`0=关闭`），不要留伪造 IP 的后门

## 3. AI 在整个开发流程中的真实作用

### 3.1 六个阶段，介入强度不同

**阶段一 · 需求与计划（AI 主导，人审批）**
AI 产出功能分级（P0–P5）、技术选型、数据模型、验收标准。
人的动作：改前端技术栈（React → Vue 3）、要求"先不写代码"、要求"先出 agent.md"。

**阶段二 · 基座与契约（AI 主导，人验收）**
骨架、迁移、健康检查、契约文档、前端壳页。这一阶段 AI 几乎不会出错，
因为**没有业务歧义，只有机械劳动**。

**阶段三 · 数据与检索（AI 主导，人提供凭据）**
seed、灌库、只读 API、越权拦截、检索评测。
人在这里做了一件关键的事：**自己填 key，填完才让 AI 跑测试**。
这不是形式主义——它把"凭据"和"代码"的责任边界划清了。

**阶段四 · 对话主链路（AI 主导，人定"什么算对"）**
图、节点、SSE、前端流式。AI 写得很快，但"3 轮指代接续正确"这个验收标准是人定的。

**阶段五 · 业务闭环（人机拉锯最多）**
售后受理的每个分支都有业务歧义：什么算可受理？确认词怎么判？重复提交怎么办？
AI 给方案，人做取舍，AI 把取舍写成代码和测试。

**阶段六 · 质量与交付（AI 执行，人校准口径）**
限流、计量、看板、评测、UI 打磨、演示脚本。门槛是人定的，数据是 AI 跑的。

**点评**：AI 的可靠性随"业务歧义密度"下降，不随"代码难度"下降。
本项目里最难的不是 LangGraph，而是"确认词怎么判"这种**没有标准答案的判断**。

### 3.2 AI 做得好的三类事

1. **机械一致性**：15 张表、20 个端点、6 个工具，命名和结构高度一致，
   人写会累到走样，AI 不会
2. **跨文件追踪**：改一个字段要动 model / schema / service / router / 前端类型 / 测试，
   AI 能一次改全（人容易漏第 5 个）
3. **把结论变成可执行物**：你说"要防注入"，它写出正则 + 单测 + 评测用例

### 3.3 AI 容易做坏的三类事（都有本项目实例）

**第一类 · 在空环境里"验证通过"**

- 迁移加 NOT NULL 列，空库上通过，有数据的库上失败
- 测试用 `delete(ChatSession)` 整表清空，跑一次把开发者会话和评测计量全抹了

**第二类 · 把"能跑"当成"对"**

- `guard.RateLimiter` 在 `limit=0` 时 `len(bucket) >= 0` 恒真，
  关掉限流后**每一轮对话都被判超频**，第一次评测 60/60 全 blocked
- `/health` 依赖 `DbSession`，库挂时依赖注入先抛异常，探测代码根本没跑到 → 返回 500 而非 503

**第三类 · 标注/预期本身写错**

- 把 `product_info` 的期望工具标成 `get_product`，
  但它的入参是 `product_id`，单轮里模型拿不到 ID —— **标注不可达**，
  指标永远上不去，看起来像"模型不行"

**点评**：这三类错误的共同点是 **AI 不会主动怀疑自己的验证方式**。
人的价值就在这里：不是写代码，而是问"你这个结论是怎么得出的"。

### 3.4 人不可让位的四个判断

1. **边界**：不做什么（不下单、不支付、不承诺赔付）
2. **契约**：错误码语义、幂等键、事件类型 —— 改一次全链路都要改
3. **验收口径**：什么算"对"。`3 轮指代正确`、`越权泄漏 = 0`、`注入拦截 ≥9/10`
4. **偏差是否可接受**：混合检索无提升还留不留？意图 59/60 要不要删样本？

**学习提示**：这四条有一个共同特征——**它们都不是"实现问题"，而是"责任问题"**。
AI 可以给你三个方案和各自代价，但不能替你承担"选错"的后果。

### 3.5 协作接口：人给什么，AI 给什么

- 人给：目标、边界、约束（技术栈 / 不许用 X）、验收标准、凭据、审批
- AI 给：分层方案、代码、迁移、测试、脚本、文档、**偏差记录**
- 双方共同维护：`agent.md`（规范）、`IMPLEMENTATION_PLAN.md`（计划 + §13 偏差）、
  `docs/eval.md`（实测数据）

**点评**：`§13 偏差记录` 是本项目最被低估的产物。
它逐条记着"计划写的是什么、实际做成了什么、为什么"——
20 条偏差就是 20 个真实决策，比任何教程都具体。

## 4. 从需求到实现的完整流程

以 **"用户说我要退货，要能受理"** 为例，走一遍全链路。这是本项目信息密度最高的一条路径。

**第 1 步 · 需求拆成可判定的句子**
"能受理"= 有权限 + 订单状态允许 + 在时效内 + 用户确认 + 不重复建单。
**判断点**：这五个条件里，哪些是规则、哪些是模型？

**第 2 步 · 找出歧义并决策**
- 用户说"行"算确认吗？→ 算，但长度 ≤8 字
- "不用了"是确认还是取消？→ 否定优先，判取消
- 重复点两次怎么办？→ 唯一索引兜底，返回同一单号

**第 3 步 · 写进契约**
新增 `POST /after-sales`、`GET /after-sales`、`PATCH /after-sales/{id}/cancel`；
新增 `action` 事件；新增错误码 `4008`（降级）、`4009`（会话忙）。

**第 4 步 · 改数据模型**
`after_sales` 补 `source`、`updated_at`；部分唯一索引；
工单号序列。**注意有存量数据，加非空列要三步走。**

**第 5 步 · 写纯函数**
`check_eligibility(order, type, now) -> Eligibility`，不碰 DB，可穷举测试。

**第 6 步 · 写领域服务**
`create_after_sales(...)`：鉴权 → 判定 → 幂等插入 → 返回 `(ticket, created)`。

**第 7 步 · 接进图**
`after_sales_node` 四分支：拒绝 / 待确认 / 建单 / 取消。
**终态文案全模板**，模型不参与。

**第 8 步 · 前端接事件**
`action` 事件 → 确认卡片 → 点击后发确认语句 → 结果卡片。
历史消息里的卡片不可点（否则会重复提交）。

**第 9 步 · 补测试与验收**
节点级（FakeLLM）测四分支；API 级测 200 + 403 + 409；
场景脚本测"出卡片 → 确认 → 建单 → 重复确认幂等"。

**点评**：这条路径里，模型只在第 1 步和第 7 步出现，而且
**第 1 步的输出还要被规则收紧，第 7 步的文案根本不经过模型**。
"AI 应用"的工程量，大部分花在**把模型挤到它该在的位置**上。

**学习要点**：

1. 需求要拆成"可判定的句子"，否则测试写不出来
2. 每个歧义都要落成一条决策，写进文档，否则下次还会重犯
3. 纯函数先行：业务规则能脱离 DB 测，就不要拖着 DB 一起测
4. 写操作的 UI 必须能表达"未完成"状态，否则用户会重复点

## 5. 关键决策与取舍（20 条）

每条都是"当时有别的选项，为什么选这个"。

- **订单/售后走确定性链路** — 不让模型自由编排工具。代价是灵活性低，收益是"不会自己发明一个退款流程"。
- **不用 LangGraph checkpointer** — 状态权威在 DB。代价是每轮重建约 10ms，收益是双真源消失。
- **意图枚举单点定义** — prompt / 路由 / 评测共用。代价是加意图要改三处，收益是不会漂移。
- **低置信先追问，但拿到槽位就不追问** — 代价是规则略复杂，收益是"用户给了单号还被反问"这种气人体验消失。
- **写操作三段式（提议/确认/执行）** — 代价是多一次交互，收益是错操作有拦截点。
- **确认判定用规则不用模型** — 代价是可能误判长句，收益是"不"开头的否定永远不会被执行。
- **终态文案模板化** — 代价是话术略生硬，收益是幻觉面积归零。
- **幂等靠唯一索引** — 代价是迁移要写部分索引，收益是并发下也不会重复建单。
- **并发用进程内 `asyncio.Lock`** — 代价是不能多实例，收益是零额外依赖（计划 §6.5 已记明扩展路径）。
- **中断落库用独立会话 + `asyncio.shield`** — 代价是多一个连接，收益是"用户关页面"也能留下 incomplete 记录。
- **输出校验带 40 字符 hold-back** — 代价是首字慢一点，收益是单号不会被"半截流出去再替换"。
- **SSE 而非 WebSocket** — 代价是没有双向通道，收益是复用 HTTP 鉴权与中间件。
- **事件表达语义而非展示** — 代价是前端要多写一层映射，收益是换 UI 不用改后端。
- **混合检索保留但定位为降级** — 代价是每次多一路查询，收益是 embedding 挂了还能用。
- **中文分词自研 bigram** — 代价是召回略粗，收益是零依赖、装得上。
- **`llm_usage` 由 runner 统一落库** — 代价是客户端不能自己写，收益是"有消息就有账"。
- **限流只保留一份实现** — 代价是 HTTP 与会话耦合一个单例，收益是"网关说没超、守卫说超了"不会发生。
- **`/admin/metrics` 口令为空则 404** — 代价是本地要配 token，收益是不暴露后台存在。
- **测试清理用差集而非整表** — 代价是 fixture 变长，收益是跑测试不会毁掉开发数据。
- **`RATE_LIMIT_PER_MINUTE=0` 表示关闭** — 代价是要显式配置，收益是评测不用伪造 IP。

**点评**：把这 20 条读一遍会发现，**每一条的"代价"都很具体，没有一条是"没有代价"**。
如果一个技术方案说不出代价，通常说明还没想清楚。

## 6. 可复用的 AI 编程方法

### 6.1 先立规范，再让 AI 动手（context 工程）

**做法**：第一份产物不是代码，是 `agent.md`：技术栈锁定、分层铁律、命名表、
API 契约、AI 纪律 10 条、测试矩阵、DoD、禁止清单。

**为什么有效**：AI 的默认行为是"补全最可能的实现"，而"最可能"通常是网上最常见的那种。
规范的作用是把"最可能"改成本项目的"应该"。

**本项目证据**：`agent.md §7` 的 10 条纪律，后来几乎每条都对应一次真实修复
（事实边界 → compose 注入 facts 块；工具预算 → 4008 降级）。

**怎么练**：新项目第一小时不写代码，写 60 行规范。写完再让 AI 读。

### 6.2 契约先行：文档是提示词，也是验收单

**做法**：`docs/api.md` 先写请求/响应/错误码，实现完回填版本号（v0.4 → v0.5 → v0.6）。

**为什么有效**：契约把"自然语言需求"翻译成"可断言的结构"，
AI 写代码时有了明确目标，测试也有了断言依据。

**怎么练**：先写 3 个端点的契约，再让 AI 实现，看它是否会"顺手多返回字段"。

### 6.3 评测先行：先有尺子，再谈优化

**做法**：60 条标注集 + 10 条对抗集，指标与计划 §7 一致，不达标改代码不改门槛。

**为什么有效**：没有评测时，"我觉得好多了"是唯一标准；
有评测后，每次改动都有前后对比，**回归无处躲藏**。

**本项目证据**：TTFT P95 从 2.61s → 2.36s，是靠"复用连接池 + 瘦身 facts 块"两项真实优化，
而不是把门槛从 2.5s 改成 3s。

### 6.4 假件替换：让模型变成可测依赖

**做法**：`tests/fakes/fake_llm.py` 固定输出，节点测试不碰真实模型。

**为什么有效**：模型的输出不确定，但**节点的逻辑必须确定**。
假件把"测逻辑"和"测模型"分开，前者能进 CI，后者进评测脚本。

**怎么练**：给你的 Agent 写一个 `FakeLLM`，让它能按顺序返回预设 plan。
写不出来，通常说明节点里塞了太多逻辑。

### 6.5 证据驱动：不认"应该能跑"

**做法**：每个阶段结束都跑真实入口，保留输出：`/health` 双 ok、`hit@3 = 10/10`、
`21/21 场景`、`scrollWidth == clientWidth == 375`、停库后 `503 + db:down`。

**为什么有效**：AI 很擅长生成"看起来对"的总结。
只有可复现的命令输出能把"看起来"变成"是"。

**怎么练**：每次让 AI 交付，追一句"**这条结论是哪条命令得出的？把输出贴出来**"。

### 6.6 小步提交 + 可回滚

**做法**：P0–P5 六个提交，每个都能独立 revert；迁移必须可 downgrade。

**为什么有效**：AI 一次改 30 个文件时，出问题很难定位。
按阶段提交，至少能二分到"是哪一阶段坏的"。

### 6.7 偏差记录：把"妥协"变成资产

**做法**：`IMPLEMENTATION_PLAN.md §13` 逐条记：原计划 / 实际 / 理由，共 20 条。

**为什么有效**：妥协不记录，三个月后就会有人（包括你自己）重新踩一遍。
记录之后，它就是**这个项目独有的知识库**。

**怎么练**：每次"计划外"的决定，花 30 秒写三行。

### 6.8 主动制造失败：安全与降级要演练

**做法**：注入话术、越权查单、停掉数据库、把接口打回 429、把视口压到 375×420。

**为什么有效**：正常路径 AI 会写，异常路径才是事故来源。
停库那次直接暴露了 `/health` 返回 500、前端只看到"服务内部错误"两个问题。

**怎么练**：每个功能上线前问一句"**它怎么坏？坏了用户看到什么？**"

## 7. 如果重做一次

**会改的三件事**

1. **评测集提前到 P2**：现在是 P4 才建，导致 P2/P3 的改动只能靠场景脚本"感觉对"。
2. **事实支撑率改成人工抽查表 + 采样脚本**：锚点覆盖率只能当下限，一开始就该设计成两层。
3. **`.env` 的 key 校验前置到启动**：现在缺 key 要到灌库或首轮对话才报错。

**不会改的三件事**

1. **不用 checkpointer**：这一条省掉的排查成本，比省下的重建成本大得多。
2. **写操作三段式**：多一次点击换来"错操作有拦截点"，值。
3. **契约先于代码**：这是唯一让"AI 写 90% 代码"还能维护的原因。

## 8. 四周复刻路径（如果你想自己走一遍）

- **第 1 周**：跑通五条命令 + 读 `agent.md` + 读 `docs/api.md`。
  目标：能说清一次请求穿过哪几层。**产出：一张自己的架构图。**
- **第 2 周**：拆掉 `after_sales` 节点，自己按"鉴权 → 判定 → 确认 → 幂等"重写一遍。
  目标：理解为什么确认判定不能交给模型。**产出：节点测试 4 个分支。**
- **第 3 周**：加一条新意图（例如"修改收货地址"），从枚举 → prompt → 路由 → 节点 → 契约 → 测试全走一遍。
  目标：体验"加一个意图要动几处"。**产出：一次完整提交。**
- **第 4 周**：写 10 条自己的评测用例，跑 `eval.py`，把不达标的项改到达标（不许改门槛）。
  目标：体验"用数据驱动 prompt 改动"。**产出：一份前后对比。**

## 附录 A · 踩坑索引（症状 → 根因与解法）

- **`alembic.ini` 报 UnicodeDecodeError** — 文件里写了中文，配置读取按 GBK。保持纯 ASCII，DSN 移进 `env.py`。
- **前端 `127.0.0.1:5173` 502** — Vite 7 只监听 `[::1]`。用 `localhost` 访问。
- **测试报 "Event loop is closed"** — 模块级 engine 跨事件循环。结束时 `dispose_engine()`。
- **装 `jieba` 失败** — 只有 sdist，构建期要批量删临时文件，被安全策略拦。改自研 bigram。
- **注册测试残留账号** — 用例没回收。改为按唯一键精确删。
- **单号识别在中文里失效** — `\b` 对中文字符不成立。改 `(?<!\d)…(?!\d)`。
- **上一轮关键词污染本轮检索** — 用了跨轮持久的 `slots.keyword`。检索只用本轮输入。
- **路由拼出 `/sessions//messages`** — Vue Router 可选参数是空串不是 `undefined`。加 `length > 0`。
- **有数据的表加 NOT NULL 列失败** — 走"加可空 → 回填 → 改非空"。
- **mypy 报 langgraph `astream` 类型不符** — 用 `cast("tuple[str, Any]", item)`。
- **用户给了单号仍被反问** — 低置信闸门挡在槽位判定前。先判槽位再判置信。
- **多意图问句只答一半** — `order_flow` 里补 `_looks_policy_question` 顺带检索。
- **关掉限流后所有对话被判超频** — `len(bucket) >= 0` 恒真。统一到一份实现，0 表示关闭。
- **跑测试后看板"有成本、没轮次"** — 测试整表清空。改"差集 + 按 id 回收"，无外键子表要显式删。
- **停库时前端只看到"服务内部错误"** — asyncpg 抛 `ConnectionRefusedError`，不是 `SQLAlchemyError`。两个 handler 都要注册。
- **越权回答出现"查不到订单 另一笔订单 的物流"** — 流式切点把"订单"和单号切开。加边界保护并测 1/2/3/5 字符分片。
